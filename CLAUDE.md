# CLAUDE.md: local-saas

Technical guide for working in this repo. README.md is the usage-oriented entry point; this file documents non-obvious design decisions, verified in practice, so they don't get rediscovered.

## Deployment

```bash
source /path/to/bash-aliases/.bash_aliases.d/local-cluster-functions.sh   # only if using --cluster-mode kind
source /path/to/local-saas/saas.sh
```

All internal paths are resolved via `BASH_SOURCE` (see `saas.sh` and `services/gitlab/gitlab.sh`), never hardcoded. `kind_cluster` is referenced only by function name (`command -v kind_cluster`), never by any PC's absolute path.

## Writing style

**Language: English.** All code comments, log/prompt/error messages, `--help` text, and README.md content must be in English. This is a standing user preference, not scoped to any one file. This file (`CLAUDE.md`) is written in English too, though it's exempt from the rule below (see next paragraph): write it in whatever form is most useful for Claude to consume in future sessions.

**No artificial line wrapping** in `README.md` and in comments inside this repo's Bash code and YAML manifests: one line of text should be one whole paragraph, not cut at an arbitrary fixed width. Only break a line when the content itself justifies it for readability, such as enumerations, numbered steps, lists, or tables, never as a width convention. This specific rule does NOT apply to `CLAUDE.md` files (this one, or the one at the root of `SaaS local/`): their content is written in whatever format is most optimal for Claude's own consumption, not necessarily unwrapped.

**No em dashes.** Never use `—` as a punctuation mark in anything contributed to this repo (code comments, docs, YAML). If a sentence would reach for one, rephrase it instead: split it into two sentences, use a comma or colon, or restructure the clause. Do not substitute a plain hyphen either, since that reads as a typo. A standing user preference, not scoped to this repo alone (see `SaaS local/CLAUDE.md`, outside this repo, for the general rule).

## Design notes: findings verified in practice

- **The `gitlab/gitlab` chart no longer bundles PostgreSQL/Redis/MinIO** (confirmed live with `helm show values gitlab/gitlab` against version 10.3.x / GitLab 19.3.x: there's no top-level `postgresql:`, `redis:`, or `minio:` key at all, only "External PostgreSQL... External Redis" comments in the header). That's why this repo deploys its own PostgreSQL/Redis/MinIO. The two modes now diverge in how: `--mode dev` keeps the original single-instance plain manifests (`datastore.sh`, no third-party chart, no HA; deliberate, since a disposable local cluster gains nothing real from HA), while `--mode prod` deploys genuine HA **unconditionally** (`datastore-ha.sh`): PostgreSQL via the [CloudNativePG](https://cloudnative-pg.io/) operator (3 instances, real automatic failover), Redis via [OT-CONTAINER-KIT/redis-operator](https://github.com/OT-CONTAINER-KIT/redis-operator) (Sentinel-based, 3 nodes), MinIO in its own 4-node distributed mode (`datastore.sh`'s `_saas_gitlab_datastore_minio_ha_apply`; MinIO clusters itself via a multi-host server argument, no operator needed).
  - Bitnami's charts were considered and explicitly ruled out for this: since August 2025 Bitnami's free tier only ships `:latest` (no version pinning) for a reduced image set, and the full versioned catalog moved behind a paid subscription, incompatible with this repo's hard requirement to pin exact third-party versions (see "Pinned versions" below). `spotahome/redis-operator` (a cleaner API than OT-CONTAINER-KIT's) was also considered and ruled out: archived upstream since June 2026, no security/compatibility fixes going forward.
  - **Known trade-off, deliberate**: the `RedisSentinel` CR is created WITHOUT its own `kubernetesConfig.redisSecret`, leaving the Sentinel port (26379) unauthenticated, while the actual Redis data connection (`RedisReplication`'s `redisSecret` plus `redisSentinelConfig.redisReplicationPassword`) stays fully password-protected: `global.redis.sentinelAuth.enabled: false` in `values/datastore-ha.yaml.tpl`. This routes around a currently-open upstream bug (`OT-CONTAINER-KIT/redis-operator` issue #1871: authentication on the embedded-sentinel path). Sentinel only ever exposes topology/monitoring info, never data, so this was judged an acceptable trade-off rather than blocking the feature on an upstream fix. Revisit once that issue is resolved.
  - **The Sentinel master group name is NOT hardcoded.** An initial research pass assumed redis-operator fixed it to `"mymaster"`; verified live (chart 0.26.1) it's actually a real, settable field (`RedisSentinel.spec.redisSentinelConfig.masterGroupName`) whose own default is `"myMaster"` (mixed case) if left unset. Reproduced live: querying Sentinel for `mymaster` (lowercase) when the group is actually named `myMaster` returns `ERR No such master with that name`, so GitLab's Sentinel-aware Redis client would never find the master. `datastore-ha.sh` now sets `masterGroupName: mymaster` explicitly on the `RedisSentinel` CR so it matches `global.redis.host: mymaster` in the values overlay. Never rely on this operator's implicit default.
  - **`RedisReplication`/`RedisSentinel` do NOT expose a `status.conditions` field** in this chart version (confirmed against the installed CRD's OpenAPI schema: `status` only has `connectionInfo`/`masterNode` for `RedisReplication`, and is entirely untyped for `RedisSentinel`). `kubectl wait --for=condition=Ready` on either resource hangs until timeout no matter how healthy the underlying pods actually are (reproduced live: both StatefulSets were `3/3` ready throughout). `datastore-ha.sh` waits on the underlying StatefulSets instead (`<release>-redis` and `<release>-redis-sentinel`, the latter confirmed from the operator's own service-naming source). Do the same for any future check against these two CRDs; don't assume `condition=Ready` exists just because it does for CNPG's `Cluster` (which genuinely has it). The Sentinel StatefulSet specifically is also NOT created immediately when its CR is applied (observed live, over a minute's delay after the RedisReplication StatefulSet is already rolled out, apparently because the operator waits for the replication side to settle first), so `datastore-ha.sh` polls for its existence before calling `kubectl rollout status` on it (see `_saas_gitlab_wait_for_resource`), since `rollout status` fails immediately with `NotFound` rather than waiting for a resource that doesn't exist yet.
  - `--mode dev`'s Redis deliberately stays password-less (`global.redis.auth.enabled: false`, unchanged). A disposable, ClusterIP-only local cluster gains no real security from a password, and the HA/security hardening above is explicitly scoped to `--mode prod` only.
- **PostgreSQL must be >= 17** for GitLab 19.3.x (with 16, the `db:schema:load` migration explicitly warns "requires PostgreSQL >= 17" and later fails). `datastore.sh` uses `postgres:17-alpine`.
- **The default `max_locks_per_transaction` (64) isn't enough** to load GitLab's full `structure.sql` in a single transaction: it fails with `ERROR: out of shared memory / HINT: increase max_locks_per_transaction` partway through `db:schema:load`. Raised to 256 via `args: ["-c", "max_locks_per_transaction=256", ...]` on the PostgreSQL container.
- **The `toolbox` pod goes into `CrashLoopBackOff` if it isn't given an `.s3cfg`**, even when no backup functionality is ever used: its startup command (`gitlab/charts/gitlab/charts/toolbox/templates/deployment.yaml`) unconditionally runs `cp /etc/gitlab/.s3cfg $HOME/.s3cfg && sleep ...` whenever `backups.objectStorage.backend` is `s3` (its default), without that file being mounted unless `backups.objectStorage.config.secret/.key` is explicitly configured. `datastore.sh` generates an extra secret (`<release>-datastore-s3cfg`, `s3cmd` format) pointing at the same MinIO, and the values overlays reference it under `gitlab.toolbox.backups.objectStorage.config`. Without this, `saas gitlab runner` (which mints the `root` PAT via `kubectl exec` on this pod) doesn't work either.
- **The real KAS toggle is `global.kas.enabled`, NOT `gitlab.kas.enabled`**, verified with `helm template` against the real chart: `gitlab.kas.*` doesn't error (Helm doesn't validate unknown keys by default) but does nothing either, so KAS kept installing anyway until this was fixed. `gitlab-pages`, by contrast, is disabled by default already (`global.pages.enabled: false` out of the box), so it didn't need touching.
- **`global.gatewayApi.configureCertmanager` defaults to `true`**, even when Gateway API isn't used at all. With `installCertmanager: false` but without disabling this too, `helm template`/`install` fails hard demanding `certmanager-issuer.email` (a subchart that should only activate with classic Ingress plus `configureCertmanager`, but the real condition is an `OR` across configureCertmanager, ingress, and gateway). The overlays set `global.gatewayApi.enabled/installEnvoy/configureCertmanager` all three to `false` explicitly (Gateway API isn't used in this project).
- **We have to set the initial `root` password ourselves, never let the chart invent it on its own**: GitLab only sets that password in the database the first time it boots with no admin user at all. If, after `saas gitlab down`/`up` (which destroys the cluster, and with it the `Secret`, but preserves the PostgreSQL data on the host), `shared-secrets` were left to generate a new random `Secret`, that value would no longer match the real hash stored in the persisted database, breaking login after every `up`. That's why `install.sh` generates `ROOT_PASSWORD` once, persists it in the state (same as `PSQL_PASSWORD` and the MinIO credentials), and creates the `Secret <release>-gitlab-initial-root-password` itself BEFORE installing the chart, referenced via `global.initialRootPassword.secret/.key`. The same pattern applies to all three credentials, not just PostgreSQL/MinIO.
- **`install` (not just `up`) must reuse existing credentials on a release that's already provisioned.** `_saas_gitlab_provision` generates a fresh random PostgreSQL/MinIO/root/Redis password whenever it's passed an empty one; `up` already avoided this by loading `SAAS_GITLAB_STATE_*` first, but `install` didn't, so re-running `install` against an existing release silently regenerated all four credentials without restarting the already-running PostgreSQL/MinIO/Redis pods (Kubernetes doesn't restart a pod just because the Secret it reads from changed), leaving the pods and every fresh Secret consumer out of sync. `install.sh` now loads saved state first, same as `up`, and passes those credentials through when present.
- **`kind` doesn't reliably support `docker stop`/`docker start` of its nodes** (open, unresolved issues in kubernetes-sigs/kind: #148, #1867), confirmed by research and not deeply tested here because the chosen approach (`down`/`up` = destroy-while-preserving-data / recreate-and-reinstall) doesn't need it: `kind_cluster delete` without `--purge-storage` always left the data in `KIND_CLUSTER_STORAGE_DIR/<name>/...` (host-side, outside the cluster's lifecycle), so a later `create` with the same name plus a `helm upgrade --install` with the same persisted credentials reconstructs the same state. Cost: several minutes of startup, not an instant resume. An instant-resume alternative (a VM with `multipass suspend`) was evaluated as a preliminary design but not implemented here.
- **Deliberate exception to "no state file of its own"** (`kind_cluster`'s convention): `saas gitlab` does need one (`services/gitlab/lib/state.sh`, `~/.local/state/saas/gitlab/<release>.env`) because the `down`/`up` cycle destroys EVERY Kubernetes object of the release (namespace, Secrets, everything). Without saving the install parameters and the three generated credentials (PostgreSQL, MinIO, root) to disk, `up` couldn't reconstruct a state compatible with the already-persisted data. `kind_cluster` doesn't have this problem because it never destroys anything it later has to reconstruct with the same secrets.
- **`--dns-provider duckdns` is implemented via a third-party webhook**: `cobexer/cert-manager-webhook-duckdns` (OCI chart `oci://ghcr.io/cobexer/charts/cert-manager-webhook-duckdns`, pinned version in `operators.sh`). This is the ONE deliberate exception in this repo to "cert-manager-native DNS-01 providers only" (`cloudflare` stays native, no webhook); any future provider needing a webhook requires an equally explicit, case-by-case decision, not a precedent from this one. Two earlier candidates were found and rejected first: `nolte/cert-manager-webhook-duckdns` (archived) and its fork `ebrianne/cert-manager-webhook-duckdns` (no release since Dec 2023, its GitHub Pages chart repo returns 404). `cobexer`'s is a continuation of that same lineage, actively maintained (Renovate-bot dependency updates) at the time this was implemented. The webhook's own RBAC scopes its Secret-read permission to exactly ONE fixed secret name (`cert-manager-webhook-duckdns-token` in the `cert-manager` namespace), so it's a single, cluster-wide shared DuckDNS account token, not one per release. The last `install`/`up` using `--dns-provider duckdns` to run updates it for every release in that cluster (documented behavior, not a bug).
- **Container Registry and GitLab Pages are implemented**, both usable in `--mode dev` and `--mode prod`, via optional `--registry`/`--no-registry` (default: **on**) and `--pages`/`--no-pages` (default: **off**) flags. Asymmetric defaults, deliberate: Registry is a baseline expectation with low cost (one more Deployment, its bucket already existed), while Pages carries its own subdomain/TLS-SAN footprint most local/CI-only installs won't need.
  - Container Registry needs its own storage config (confirmed: it does NOT reuse `global.appConfig.object_store`; `registry.storage.secret` is a separate Secret whose `config` key is the registry's native S3-driver YAML, spliced into its `config.yml` at startup by the subchart's own init script). `datastore.sh` always creates this secret (`<release>-datastore-registry-storage`), same precedent as the always-created `.s3cfg`.
    - **That S3 storage config needs `pathstyle: true`, `checksum_disabled: true`, and `redirect.disable: true` to actually push/pull images against MinIO**, not just point at it. `checksum_disabled` is GitLab's documented fix for its registry's S3 v2 driver (confirmed as `DriverName s3_v2` in the registry's own logs despite the config using the `s3` key) sending a CRC64NVME checksum on multipart `UploadPartCopy` that MinIO rejects with `InvalidArgument: checksum missing`; known remaining limitation from that same GitLab guidance: a push that triggers `DeleteObjects` can still fail, no equivalent knob for that path. `pathstyle` is GitLab's documented recommendation for MinIO/Ceph RGW. `redirect.disable` avoids the registry 302-redirecting blob requests to MinIO's internal ClusterIP address, unreachable by any client outside the cluster's pod network (manifest/auth resolve fine over the public ingress; only the blob download fails without this). Checked and confirmed NOT needed on `<release>-datastore-objectstore` (the Fog/aws-sdk-ruby connection GitLab's Rails app itself uses for artifacts/LFS/job traces): `path_style: true` was already set there, GitLab's checksum workaround for that different S3 client is delivered via `AWS_REQUEST_CHECKSUM_CALCULATION`/`AWS_RESPONSE_CHECKSUM_VALIDATION` env vars rather than a connection key, and the redirect issue is registry-specific (Rails always talks to MinIO over the internal Service address).
  - Both `registry.<domain>` and `pages.<domain>` are added as extra SANs on the SAME certificate as the main domain (`tls.sh`'s `_saas_gitlab_certificate_request`, now variadic). No second certificate, no wildcard.
  - **Pages TLS decision**: `global.pages.namespaceInPath: true` by default (path-based Pages URLs, `pages.<domain>/group/project/`) instead of the chart's native subdomain-based routing (`group.pages.<domain>/project`, confirmed in `charts/gitlab/charts/gitlab-pages/templates/ingress.yaml`: the Ingress host becomes `"*.{{ hostname }}"`, a single wildcard level, not a doubly-nested one), which would require a WILDCARD `*.pages.<domain>` certificate, obtainable only via DNS-01. `namespaceInPath: true` keeps Pages working with self-signed/HTTP-01 TLS too, at the cost of a less conventional Pages URL shape. Documented trade-off, not an oversight.
    - **Opt-in alternative**: `--pages-url-mode subdomain` (`install.sh`) switches to the chart's native routing. Cross-validated to require either `--tls self-signed` (the ClusterIssuer signs a wildcard SAN locally, no ACME/CA validation involved at all, so DNS-01 isn't actually needed there) or `--tls letsencrypt --challenge dns01` (the only ACME challenge that can prove ownership of a wildcard name for a real CA-trusted cert); `_saas_gitlab_valid_pages_subdomain_tls` in `install.sh` is the pure predicate. The wildcard `*.pages.<domain>` `Certificate`/`Secret` is a SECOND, standalone one (`_saas_gitlab_certificate_request` called again with a wildcard DOMAIN), never a SAN on the shared certificate, so the main domain's TLS/challenge stays untouched either way; it's wired to the Pages Ingress via `gitlab.gitlab-pages.ingress.tls.secretName`, a per-component override the `gitlab-pages` subchart's own `pages.tlsSecret` helper checks before falling back to the shared `global.ingress.tls.secretName` (verified against the real chart with `tools/helm-chart-extract-values.sh`, not documented anywhere in the umbrella chart's merged `values.yaml`).
    - `--cluster-mode kind` also needs a second, independent CoreDNS patch for this mode (`_saas_gitlab_cluster_patch_coredns_pages_wildcard`, `cluster.sh`): the `hosts` plugin `_saas_gitlab_cluster_patch_coredns` already uses only matches exact names, never wildcards, but Pages' per-namespace subdomains are arbitrary and unknown at install time. Solved with CoreDNS's `template` plugin instead, in its own marker-delimited block so it can be toggled independently of the `hosts` block. Not needed (and not touched) in `--cluster-mode existing`, where real wildcard DNS is assumed to already exist outside this repo.
    - **Local workaround, no DNS provider account needed**: with `--tls self-signed`, `--domain <host-ip>.nip.io` (e.g. `127.0.0.1.nip.io`, matching kind's hostPort exposure) resolves every Pages subdomain automatically from the host's browser, with zero setup, since nip.io answers any subdomain of an IP-encoded name with that same IP. This only works for DNS *resolution*, never for proving domain ownership to a real CA: nip.io's zone is controlled by that service, not by whoever installs GitLab here, so it can't satisfy a DNS-01 challenge (irrelevant for self-signed, which has no CA validation step at all). `install.sh` suggests this domain as the interactive default precisely when `--pages --pages-url-mode subdomain` and `--cluster-mode kind` are active together with self-signed TLS, and only then; every other combination keeps today's `<release>.gitlab.local` default unchanged.
    - **Verified live**: `tests/gitlab/e2e/run-tests.sh --only pages-subdomain` (`--tls self-signed --domain 127.0.0.1.nip.io`) against a real kind cluster confirms both Certificates end up `Ready`, the wildcard `Secret` is genuinely separate from the main one, the CoreDNS `template` block is present, and a made-up Pages subdomain responds (404, as expected with no site published yet). The full default E2E suite (dev-install/registry/pages/duckdns/up-down/ssh-config) was also re-run afterward and still passes unchanged, confirming this feature's `install.sh` restructuring (shared `_saas_gitlab_provision`/`_saas_gitlab_render_values_layer` signatures, Pages now resolved before `--domain`) introduced no regression on the non-subdomain path.
    - **Real bug found and fixed while testing this live** (nothing caught it beforehand, see next point): `_saas_gitlab_certificate_request` (`tls.sh`) built `dnsNames: [...]` unquoted. A wildcard DOMAIN starting with `*` is YAML's alias indicator when unquoted, so `kubectl apply` failed outright with "error converting YAML to JSON: ... did not find expected alphabetic or numeric character" the moment `--pages-url-mode subdomain` first tried to request one. Fixed by quoting every dnsName in the generated YAML (a no-op for a plain hostname).
    - **Known gap, deliberately left for manual verification, not yet exercised against a real cluster**:
      1. The `--tls letsencrypt --challenge dns01` path for `--pages-url-mode subdomain`, against a real Cloudflare/DuckDNS account. Only the `self-signed` path above was exercised live, for the same reason the `duckdns` E2E phase can't attempt real ACME issuance either (no real DNS account available in CI/dev).
      2. Toggling `--pages-url-mode` from `subdomain` back to `path` on an already-installed release, to confirm the wildcard `Certificate`/`Secret` and the CoreDNS `template` block are actually torn down cleanly on a live cluster. The CoreDNS block-removal logic itself IS unit-tested (`test-argparse-values.sh`), just never exercised end-to-end on a real release.
      Before relying on either, verify manually first; `tests/gitlab/unit/test-argparse-values.sh`'s coverage of the underlying logic is not a substitute for a real run of these two specific paths.
- **`--storage-mode` (kind) vs. `--storage-class` (existing) are mutually exclusive and validated as an explicit error**, never a flag silently ignored. See `install.sh`, the `--cluster-mode` validation section.
- **`saas gitlab doctor`'s PostgreSQL password reset uses `pg_ctl reload`, never a `psql`-issued `SELECT pg_reload_conf()`.** The fix has to edit `pg_hba.conf` to temporarily add a `local all all trust` rule, then reload it so that rule takes effect, then `ALTER USER gitlab WITH PASSWORD ...`. The tempting way to trigger that reload is `psql -c 'SELECT pg_reload_conf()'`, but that call itself still has to authenticate under the OLD rules (the very ones potentially broken), a chicken-and-egg problem. `pg_ctl reload -D "$PGDATA"` is an OS-level command against the data directory, no DB connection/auth involved at all, so it works regardless of whether the current password is valid. The original `pg_hba.conf` is always restored via a `trap ... EXIT` inside the single `kubectl exec -i ... sh -c` script, so a partial failure (e.g. `ALTER USER` itself failing) never leaves `trust` auth active.
  - Deliberately scoped to `--mode dev`'s single-instance StatefulSet only. `--mode prod`'s CloudNativePG-managed `Cluster` reconciles its own credentials/`pg_hba.conf` continuously; hand-editing it the same way would fight the operator's own reconciliation loop, so `doctor` skips PostgreSQL entirely when `SAAS_GITLAB_STATE_MODE=prod` and reports that explicitly rather than silently doing nothing.
- **MinIO secret drift is always reconciled FROM the running pod's own env, never from the saved state.** `doctor`'s source of truth for the "real" MinIO password is `kubectl exec` + `printenv MINIO_ROOT_PASSWORD` on the actual running pod, not `SAAS_GITLAB_STATE_MINIO_ROOT_PASSWORD`: the pod is what GitLab is really authenticating against, and the whole point of this check is to catch cases where the 4 derived Secrets (or the state file itself) no longer agree with it, so treating the state file as authoritative would be circular.
- **`saas gitlab doctor` is diagnose-only by default; `--fix` is required to change anything.** A deliberate choice (not the only reasonable one: an earlier design considered auto-repairing by default) so that force-deleting pods, temporarily enabling `trust` auth on PostgreSQL, and rewriting Secrets/restarting Deployments is always an explicit, opt-in action, matching common CLI conventions (`brew doctor`, `npm audit`) rather than something a bare `doctor` call does silently.
- **No flag requires a value with no default unless it's genuinely impossible to guess**: `--email`/`--domain` (with `--tls letsencrypt`) and `--dns-token` (with `--challenge dns01`) are the only three. Everything else, including `StorageClass` resolution in `--cluster-mode existing` with several ambiguous options, has a reasonable automatic default even in `--non-interactive` (warning on stderr if it had to pick among several), the same principle `kind_cluster` already uses for its prompts.

### `services/vault/`

- **`_saas_require_kind_cluster_fn`, `_saas_ensure_certmanager`, and `_saas_resolve_storage_class` were promoted from `services/gitlab/` into `lib/common.sh`** the moment `services/vault/` needed the exact same logic with zero variation, unlike the deliberately-per-service datastore operators (CNPG/redis-operator/DuckDNS webhook) which stay in `services/gitlab/lib/operators.sh` since they're genuinely GitLab-domain-specific. This is not "sharing for its own sake": with only `lib/common.sh`'s generic logging/prompt/getopt helpers shared before this, duplicating these three again would have been copying identical code with no reason, and the "rule of three" caution against premature abstraction is about not guessing at an interface's shape before it's proven - here a second real service proved it's identical. Stakater Reloader (`services/vault/lib/operators.sh`) deliberately stayed OUT of this extraction: gitlab doesn't use it today, so there's nothing yet to share; revisit only if/when a third consumer needs it too.
- **`global.tlsDisable: false` must be set explicitly in the chart values, or every `BAO_ADDR` the chart injects defaults to plain `http://127.0.0.1:8200`.** Verified live: without it, `bao operator init`/`bao status` run via `kubectl exec` (inheriting the container's own env) fail outright with "Client sent an HTTP request to an HTTPS server", even though the actual listener config (`services/vault/values/dev.yaml.tpl`/`prod.yaml.tpl`) correctly enables TLS. `install.sh`'s own `kubectl exec ... bao ...` calls additionally set `BAO_ADDR`/`BAO_CACERT` explicitly rather than relying solely on the container's env, since that's more robust and keeps the intent visible at each call site.
- **`service_registration "kubernetes" {}` is required in the Raft `config` HCL block for the chart's own `<fullname>-active` Service to ever get an Endpoint.** Without it, `bao`/OpenBao never labels its own pod as the active/leader node, so the "-active" Service (what the Helm chart's `server.ingress` targets by default, `activeService: true`) sits with zero Endpoints forever, and ingress-nginx logs `does not have any active Endpoint` while returning ITS OWN generic 503 (not a response from Vault at all) for every request. Confirmed against the real chart's own default `values.yaml` (`tools/helm-chart-extract-values.sh`), which includes this exact stanza - it's not an optional extra, the whole active/standby routing model depends on it.
- **A cert-manager `Certificate`'s private-key rotation policy is `spec.privateKey.rotationPolicy`, NOT a top-level `spec.rotationPolicy`.** Verified live: the latter fails outright with a strict-decoding error ("unknown field") against a real cert-manager v1.21.2 CRD. Easy to get wrong since some other cert-manager fields (`duration`, `renewBefore`, `secretName`) really are top-level; this one specifically nests under `privateKey`.
- **A kind cluster's default `local-path` StorageClass does NOT reliably give a PVC its old data back across `down`/`up`, even though `kind_cluster delete` (without `--purge-storage`) leaves the host-side files in place.** Verified live: `rancher.io/local-path-provisioner` names each PV's on-host directory after that PV's own (effectively random) UID - `<KIND_CLUSTER_STORAGE_DIR>/<name>/local-path-provisioner/pvc-<uid>_<namespace>_<pvc-name>` - not after the stable PVC name. A fresh `helm upgrade --install` after `up` creates a brand-new PVC/PV pair with a brand-new UID, which binds to a brand-new, empty directory; the OLD data is still physically on disk, just permanently orphaned (three such orphaned directories accumulated after three install/down/up cycles during testing, none ever reused). This affects gitlab's own PostgreSQL PVC identically, but it doesn't matter there in practice: a fresh, empty PostgreSQL just re-runs its own first-boot migration and re-applies the SAME persisted `ROOT_PASSWORD` from `state.sh`, so the end result looks identical to a user regardless of whether the underlying files survived. Vault can't paper over this the same way, since Shamir key shares are cryptographically tied to the ONE `bao operator init` call that produced them - reusing old shares against a fresh, uninitialized Raft store can never work (reproduced live: the unseal-sidecar loops forever posting old shares to a store stuck at `initialized: false`). `init.sh`'s `_saas_vault_init_ensure` therefore checks the pod's own LIVE `.initialized` status before deciding whether to reuse saved keys, not merely whether a local keys file exists; if the pod reports uninitialized despite a saved-keys file being present, it transparently re-initializes with fresh material and warns loudly that the old keys no longer apply. Documented in `saas vault up --help`/`down --help` as "whether data survives depends on the storage setup", not promised.
- **The root token/unseal keys are deliberately hidden by default in `saas vault credentials`**, unlike `saas gitlab credentials`'s plain password print: this is break-glass access to the ENTIRE secrets store, not one app's login, so `--reveal-root-token`/`--reveal-unseal-keys` are required. Both are read from the local, `chmod 600` keys file only (`secrets.sh`), never from the cluster; the root token is never written to any in-cluster object at all, only a threshold-sized subset of the unseal key shares ever is (the `unseal-keys` Secret, RBAC-scoped to `get` on exactly that one Secret name). This is a documented, deliberate trade-off, not a production-grade KMS auto-unseal replacement: anyone able to read that Secret (or exec into the pod while it's mounted) has master-key-equivalent access, though never the root token.
- **`delete` removes the saved keys file only with `--purge-storage`.** Without it, the keys are kept as a (possibly harmless, possibly still-needed) leftover: if the underlying storage genuinely survives (`--cluster-mode existing`, or a storage setup where PVCs really do rebind), a future install needs those exact shares; if it doesn't (kind's default local-path, see above), the kept keys are simply superseded by a fresh init next time, no harm done either way. `down` never touches the keys file at all, regardless of `--purge-storage` (which `down` doesn't even accept, only `delete` does).
- **`--dns-provider` only supports `cloudflare` here, deliberately narrower than gitlab's `cloudflare`/`duckdns`.** gitlab's own CLAUDE.md calls the DuckDNS third-party cert-manager webhook "the ONE deliberate exception... any future provider needing a webhook requires an equally explicit decision, not a precedent from this one" - so it was NOT extended to Vault's cluster by default, to avoid installing yet another third-party webhook operator without an equally explicit reason. Revisit only with as explicit a justification as the original DuckDNS decision.
- **Only the reviewer-token Kubernetes-auth mode is implemented for `integrate gitlab`/`integrate eso`, not JWKS-based validation.** Reviewer-token works for a kind cluster whose OIDC issuer (`https://kubernetes.default.svc.cluster.local`) isn't externally reachable, which JWKS-based validation would need. Kept out of scope deliberately to avoid the extra complexity of supporting two auth-configuration paths for a need that hasn't materialized yet.
- **The GitLab/ESO integration is deliberately two-sided (`saas vault integrate gitlab` + `saas gitlab integrate vault`), never a single command that reaches into both clusters.** This is a direct, non-negotiable consequence of the safety requirement that each tool only ever mutates its OWN cluster: `saas vault integrate gitlab`'s phase A/B design (preflight the target read-only, mutate only Vault, render manifests) can get the Vault side fully ready, but applying anything into the GitLab cluster is necessarily `saas gitlab`'s own job, since it's the tool that already legitimately owns that cluster. The reviewer-manifest handshake (apply it once, so Vault's Kubernetes auth method has something to validate tokens against) is the one unavoidable back-and-forth this implies; both commands are idempotent and safely re-runnable at any point in the sequence, and running either before its counterpart cluster/release exists yet fails cleanly with no partial mutation (verified both live, `tests/vault/e2e/run-tests.sh --only integrate-gitlab-order-independence`, and via mocked call-counters in the unit suite).
- **GitLab's datastore Secret names/keys are reused verbatim as the Vault KV path's field names** (`psql: {username, password}`, `minio: {rootUser, rootPassword}`, `objectstore: {connection}`, `s3cfg: {config}`), matching `services/gitlab/lib/datastore.sh`'s `_saas_gitlab_datastore_secrets_apply` exactly, so the generated `ExternalSecret`'s `remoteRef.property` values need zero translation and stay correct even if gitlab's own datastore backend (dev vs. HA) changes, since both already produce byte-identical Secret shapes.
- **`kubectl exec -i` (stdin forwarding) is required for `bao write PATH -`/`bao policy write NAME -`-style calls carrying a JSON/HCL payload** (`_saas_vault_bao_exec_stdin`, `integration_common.sh`): argv-based `key=value` pairs handle multi-line values (a PEM CA certificate, an HCL policy) poorly, so these go through stdin instead. A separate helper from the non-stdin `_saas_vault_bao_exec`, since adding `-i` unconditionally would change behavior (and mocking) for every other call site too.
- **The "left side of a pipe runs in a subshell" gotcha (already documented for gitlab's own CoreDNS unit test) applies here too**: `services/vault/lib/init.sh`'s `kubectl create secret ... --dry-run=client -o yaml | kubectl apply -f -` pattern means a test mock that tries to capture the first `kubectl`'s arguments into a plain shell variable silently loses that assignment the instant the pipe's subshell exits; `tests/vault/unit/test-argparse-values.sh` writes to a temp FILE instead, for the same reason.
- **ESO's `v1beta1` API for `SecretStore`/`ExternalSecret`/`ClusterSecretStore` is no longer SERVED by a current External Secrets Operator install**, even though the CRD still lists it under `spec.versions` (with `served: false`) - `kubectl apply` fails outright with "no matches for kind ... in version ... : ensure CRDs are installed first", a confusing error for what's actually a stale apiVersion, not a missing CRD. All of `services/vault/values/gitlab-*.yaml.tpl`/`eso-*.yaml.tpl` use `external-secrets.io/v1`. Verified live against a real ESO chart install (`helm install external-secrets external-secrets/external-secrets --set installCRDs=true`); re-check `kubectl get crd secretstores.external-secrets.io -o jsonpath='{range .spec.versions[*]}{.name}: served={.served}{"\n"}{end}'` before assuming either version if this ever needs revisiting.
- **A namespaced `SecretStore` is REJECTED by ESO's own admission webhook if `auth.kubernetes.serviceAccountRef.namespace` differs from the SecretStore's own namespace** ("namespace should either be empty or match the namespace of the SecretStore for a namespaced SecretStore") - exactly the shape `saas vault integrate gitlab`'s design produces (a SecretStore created in the GITLAB namespace, needing to authenticate as ESO's controller ServiceAccount, which lives in ESO's OWN namespace, normally different). `gitlab-secretstore.yaml.tpl`/`eso-secretstore.yaml.tpl` use `ClusterSecretStore` instead (cluster-scoped, explicitly allowed to reference a ServiceAccount in any namespace - the entire reason it exists), named per-GitLab-release (`${vault_release}-vault-${gitlab_release}`, not just per-Vault-release) since ClusterSecretStore names share one cluster-wide namespace, unlike a per-namespace SecretStore. `ExternalSecret.spec.secretStoreRef.kind` updated to match. Verified live: the identical namespaced-SecretStore shape was rejected with this exact message before the fix, and the ClusterSecretStore version was accepted and the ExternalSecrets progressed past `SecretSyncedError`'s earlier `InvalidProviderConfig` stage.
- **The `openbao/openbao` chart's own default `server.affinity` is a REQUIRED pod anti-affinity by hostname** (`podAntiAffinity.requiredDuringSchedulingIgnoredDuringExecution`, matching `app.kubernetes.io/name: openbao` + `app.kubernetes.io/instance: <release>` + `component: server`), meaning every HA replica must land on a DIFFERENT node. Verified live: on this tool's own default `--cluster-mode kind` single-node cluster, `--mode prod`'s pod-1/pod-2 were left PERMANENTLY stuck `Pending` (`FailedScheduling: 0/1 nodes are available: 1 node(s) didn't match pod anti-affinity rules` - confirmed after waiting 3+ minutes with no change, not a slow-converging race), while `saas vault install` itself had ALREADY reported success and exited 0, since nothing waited on anything past pod-0. `values/prod.yaml.tpl` now overrides `server.affinity` to the SAME labelSelector/topologyKey but as `preferredDuringSchedulingIgnoredDuringExecution` (weight 100) instead: a real multi-node target (more kind workers, or `--cluster-mode existing` against one) still gets genuine per-host spreading, while the tool's own single-node default no longer deadlocks. Paired with a second, independent fix: `install.sh` now calls `_saas_vault_wait_ha_replicas_unsealed` (`init.sh`) after pod-0 unseals, for `--mode prod` only - it polls the LAST replica's own unseal status, which transitively proves every earlier one already got there too, since the chart's StatefulSet uses `OrderedReady` (pod-N isn't even created until pod-(N-1) reports Ready). Without this second fix, `install` would still report success right after pod-0 alone, even with the affinity fixed, since nothing else forced it to wait for the other two. Verified live end to end: all 3 replicas unseal and `bao operator raft list-peers` reports 3 voters.
- **`jq`'s `//` alternative operator falls through on BOTH `null` AND `false`, not just "missing/null".** A real bug this surfaced with, not a hypothetical: `tests/vault/e2e/run-tests.sh`'s `prod-ha` phase used `jq -r '.sealed // "unknown"'` to read `bao status`'s JSON, meaning the expression fell through to `"unknown"` every single time `sealed` was genuinely `false` - the ONE value the check existed to detect - so it could never pass, no matter how long the wait or how healthy the real cluster was (confirmed live: every failing run's raw JSON already had `"sealed": false`; three separate "fixes" chasing an assumed timing race - explicit `BAO_ADDR`/`BAO_CACERT` env, per-pod retry polling - correctly ruled out other causes but didn't touch the real bug, since none of them were it). Fixed by dropping the `// "unknown"` fallback entirely (`services/vault/lib/credentials.sh`'s `_saas_vault_verify_status`, used by every OTHER status check in this project, already did this correctly: plain `jq -r '.sealed'`, no fallback). `services/vault/lib/init.sh`'s own `.initialized // false` is a coincidental exception that stays correct either way: its fallback value is the string `"false"`, identical to what `.initialized` itself would print when actually `false`, so the two branches are indistinguishable in that one specific case - not a pattern to copy elsewhere. Rule of thumb: never use `// default` against a field whose real, valid value can itself be `false` (or `null`); use plain field access, or an explicit `if .x == null then default else .x end`, instead.
- **`auth/kubernetes/config`'s `kubernetes_host` must be an address Vault itself can reach from wherever Vault runs, NOT necessarily one reachable from inside the target (GitLab) cluster's own pod network.** `_saas_vault_target_api_server` (`integration_common.sh`) reads this from the target's kubeconfig context (`kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.server}'`), which for a local kind cluster is typically `https://127.0.0.1:<random-port>` - correct and reachable when Vault and the target are genuinely separate clusters (or hosts), since that's the host-side address kind maps the target's API server to. Live-testing this specific integration end-to-end on a SINGLE machine hits an unavoidable topology conflict outside this project's control: `kind_cluster`'s `--expose-mode ingress-nginx` hardcodes host ports 80/443, so two `--cluster-mode kind` services can never run simultaneously (see the `local-path` storage-class note above for the same class of constraint); working around it by installing GitLab into Vault's OWN cluster (a same-cluster stand-in, `--cluster-mode existing`) reproduces every real code path faithfully EXCEPT this one, where `127.0.0.1:<port>` (correct for a genuinely separate cluster) is naturally unreachable from a pod inside the SAME cluster it was captured from (loopback resolves to the pod itself, not the host). Confirmed live up to exactly this point, now via the actual scripted `tests/vault/e2e/run-tests.sh --only dev-install,integrate-gitlab-full,eso-round-trip` phases (not just ad hoc manual commands): KV engine, Kubernetes auth enable/configure, policy/role creation, credential seeding (byte-identical to gitlab's real live PostgreSQL Secret), and even the final `SecretStore`/`ExternalSecret` apply (once a throwaway ESO is present, see the next note) all succeed for real; only the final ESO-to-Vault data fetch (`ExternalSecret` stuck `SecretSyncedError: could not get secret data from provider`) was left unverified by this same-cluster workaround, for a reason specific to the workaround, not the feature. Two real, separate clusters (or a manual CoreDNS `hosts` entry mapping the domain to the ingress ClusterIP, as done ad hoc to confirm the above) resolve it.
- **`integrate-gitlab-full`'s own "final manifests applied" assertion needs a real ESO already installed in-cluster**, since `saas gitlab integrate vault` correctly refuses a partial apply of `SecretStore`/`ExternalSecret` when ESO's CRDs aren't present yet (by design, see the two-sided-handshake note above) - this was a genuine phase-ORDERING bug in the E2E script itself (not the product): the throwaway ESO used to be installed only in the separate, later `eso-round-trip` phase, so `integrate-gitlab-full`'s own final-apply step would always hit "ESO isn't installed" first, even when run correctly. Fixed by installing the throwaway ESO as part of `integrate-gitlab-full` itself (a real prerequisite of that phase's own assertion, not a separate concern); `eso-round-trip` now reuses it rather than re-installing.
- **Uninstalling ESO BEFORE deleting the `ExternalSecret` objects it manages leaves their namespace stuck `Terminating` forever**, the same finalizer-orphaning problem as the general "stuck `Terminating` namespace" class of Kubernetes gotcha, but worth naming explicitly since it silently hung this project's OWN E2E cleanup twice during this work: with ESO's controller gone, nothing is left to clear the `ExternalSecret`s' `externalsecret-cleanup` finalizer, so the namespace (and anything waiting on `saas gitlab delete` to finish deleting it) hangs indefinitely - recoverable only by manually stripping the finalizers (`kubectl patch externalsecret NAME --type=json -p='[{"op":"remove","path":"/metadata/finalizers"}]'`). `tests/vault/e2e/run-tests.sh`'s unified `cleanup()` now deletes the gitlab release (and with it, its `ExternalSecret`s, while ESO's controller is still running to process them) BEFORE uninstalling ESO, never the reverse. General lesson for future test/cleanup code in this repo: always tear down CRs before the operator that owns their finalizers, not after.
- **The `dev-install`/`up-down` phases' "root token authenticates against the API" check needs a short retry, not a single bare `curl`.** Verified live (twice, both times self-resolved within seconds): right after `_saas_vault_wait_unsealed` confirms the pod itself reports `sealed: false`, an authenticated call through the ingress can still occasionally get an empty response for a few seconds longer, apparently while the Endpoint/ingress-nginx chain finishes catching up - a manual re-check of the exact same instance moments later always succeeded cleanly. Both call sites in `tests/vault/e2e/run-tests.sh` now retry up to 6 times, 5s apart, before failing. The `/v1/sys/health` check right above it was never actually affected: it already accepted `503` (OpenBao's own documented "sealed" response code) as a pass.

### `services/minio/`

- **Standalone MinIO reuses `services/gitlab/lib/datastore.sh`'s exact manifests, generalized, not a rewrite.** `services/minio/lib/backend.sh`'s `--mode dev`/`--mode prod` shapes (single-instance Deployment+PVC; 4-node distributed StatefulSet via MinIO's own ellipsis server-pool syntax) are a direct copy of the corresponding gitlab code, since that code already had zero GitLab-specific assumptions baked into the MinIO pieces themselves (only naming). Resources are named after the release directly (`${release}`, `${release}-credentials`) rather than `${release}-minio`, since there's no longer a parent GitLab release to namespace under.
- **The two MinIO/mc image tags were promoted to `lib/common.sh` (`_SAAS_MINIO_IMAGE`/`_SAAS_MC_IMAGE`) the moment a second consumer needed them with zero variation**, same "rule of three" threshold already used for `_saas_require_kind_cluster_fn`/`_saas_ensure_certmanager`/`_saas_resolve_storage_class`. `services/gitlab/lib/datastore.sh` was updated to reference the shared constants instead of its own literals, so bumping either tag can never happen in only one of the two files by accident.
- **`mc`/`mcli` naming, a real, live conflict, not a hypothetical one**: MinIO's own client binary is named `mc`, the same name Midnight Commander uses, a conflict MinIO's own repo documents in its `CONFLICT.md` and multiple Debian/upstream issues. This repo's own `bucket.sh`/`credentials.sh --verify` never actually hit this: every `mc` invocation happens INSIDE the pinned `quay.io/minio/mc` container image (`kubectl run --rm -i`), whose rootfs has no Midnight Commander to collide with, so the code itself keeps using the upstream `mc` name internally, correctly. The conflict only matters for anything HOST-facing: README.md and this file both say to install/alias a host-side MinIO client as `mcli`, the name Debian and other distros already standardized on for exactly this conflict, not an invented repo-local convention (verify: `mc --version` on a Debian-family host is Midnight Commander, not MinIO, precisely because of this).
- **`saas gitlab integrate minio`/`saas minio integrate gitlab` is a SINGLE round trip, deliberately simpler than the Vault↔GitLab/Vault↔MinIO handshakes.** Those need a reviewer-ServiceAccount/Kubernetes-auth round trip because Vault's Kubernetes auth method has to be configured to trust tokens from a cluster it doesn't own, before it will hand out anything at all. Handing GitLab a set of static, already-known connection Secrets needs no such cross-cluster authentication trust: `saas minio integrate gitlab` renders the manifest directly (after confirming, read-only, that the target GitLab context is reachable), and `saas gitlab integrate minio` applies it, no callback needed. Don't "fix" this into a two-phase design to match Vault's shape; the two integrations solve genuinely different problems (live secret sync needing auth trust, vs. a one-time static handout).
- **GitLab's bucket list (`_SAAS_GITLAB_MINIO_BUCKETS`) is duplicated, not shared, into `services/minio/lib/gitlab_integration.sh`'s own `_SAAS_MINIO_GITLAB_BUCKETS` constant.** Same precedent as Vault's own duplicated knowledge of GitLab's Secret field names (see the note on this above, under `services/vault/`): each service only ever knows about the OTHER service's DATA shapes, never sources its CODE. A comment at the duplicate site cross-references the original by file path so the two can be kept in sync by hand if GitLab's bucket list ever changes; there is no automated check for this today.
- **The same-cluster-vs-cross-cluster endpoint decision in `saas minio integrate gitlab`, and its known gap**: if the current kubeconfig context (which MUST be MinIO's own cluster, since this command mutates it) equals the resolved GitLab context, the rendered Secrets point at MinIO's plain internal Service DNS name (`http://<release>.<namespace>.svc.cluster.local:9000`), zero TLS involved, identical in shape to GitLab's own private MinIO today. This is the realistic, PRIMARY-TESTED path (`tests/minio/e2e/run-tests.sh --only integrate-gitlab-full` installs GitLab with `--cluster-mode existing` into MinIO's own cluster, the same single-host workaround the Vault↔GitLab E2E phase already uses, for the identical reason: `kind_cluster --expose-mode ingress-nginx` hardcodes host ports 80/443, so two separate `--cluster-mode kind` services can never coexist on one host). When the contexts differ (genuinely separate clusters), the Secrets instead point at MinIO's external HTTPS ingress endpoint - a KNOWN, DELIBERATELY UNRESOLVED gap, not silently broken: no CA-trust bundle is injected into GitLab's toolbox/registry pods for a self-signed MinIO certificate in this iteration (mirrors the exact class of documented, deliberately-untested gap the Vault↔GitLab cross-cluster reachability note above already describes). `--tls letsencrypt` on `saas minio install` sidesteps the whole problem (a certificate the system's default CA pool already trusts), and is the recommended setup for a genuinely cross-cluster external object storage deployment until this gap is closed.
- **`saas vault integrate minio`'s `ExternalSecret` targets MinIO's OWN operational credentials Secret (`<release>-credentials`), not a side channel.** Unlike `eso_integration.sh`'s deliberately-placeholder KV entry (there to prove the wiring works, nothing more), this one is a real, useful rotation path: once ESO syncs a Vault-side credential change into that Secret, MinIO genuinely picks it up on its next pod restart (`saas minio doctor`/`saas minio integrate vault --help` both call this out, since Kubernetes doesn't restart a pod just because a Secret it mounts changed - the same "doesn't restart on its own" caveat gitlab's own MinIO-Secret-drift doctor check already documents).
- **No `saas minio versions` subcommand, unlike gitlab/vault.** Both of those query a live Helm chart repo for available versions; MinIO here has no chart at all (plain manifests, like GitLab's own private MinIO), so there's nothing to query. The image tags are centrally pinned (`lib/common.sh`, see above), not user-selectable via a flag - deliberate, avoids exposing a knob whose values were never validated against this deployment shape.
- **`saas minio bucket` uses `kubectl run --rm -i` (a throwaway pod), not a `Job`, unlike the install-time bucket-init path (`_saas_minio_init_buckets`, still a `Job`, same precedent as gitlab's own bucket-init).** A `Job`'s output has to be fetched separately (`kubectl logs`) after the fact; `kubectl run --rm -i` streams stdout directly back to the caller, which is what makes it fit for `bucket list` (the user needs to actually see the output), not just `bucket create`/`rm`. `--verify` on `credentials.sh` uses the same throwaway-pod technique for the same reason (and because the MinIO SERVER image, unlike the `mc` image, doesn't bundle the `mc` client at all - an early draft of `--verify` incorrectly tried to `kubectl exec` into the server pod and run `mc` there, which cannot ever work).
- **Two real, live bugs found and fixed while running `tests/minio/e2e/run-tests.sh` for real (not caught by the unit suite, which mocks `kubectl` and so never exercises the actual container invocation):**
  1. **`kubectl run --image=quay.io/minio/mc ... -- sh -c "..."` silently runs `mc sh -c "..."`, not a shell**, since the pinned image's own `ENTRYPOINT` is `["mc"]` (confirmed with `docker inspect`) and `kubectl run`'s trailing `--` args become the container's `args`, appended after the entrypoint, never replacing it. Reproduced live: every `bucket.sh` command failed with `mc: <ERROR> 'sh' is not a recognized command`. Fixed with `kubectl run --command -- sh -c "..."` (`--command` replaces the entrypoint outright), in both `bucket.sh`'s `_saas_minio_mc_run` and `credentials.sh`'s `--verify`. Curiously, `kubectl run image -- mc alias set ...` (no `sh -c`, so the redundant "mc" from the entrypoint duplication) DOES work, matching MinIO's own documented `docker run minio/mc mc alias set ...` usage pattern - but a COMPOUND command (`alias set && mb`, needed for `bucket.sh`) has no shell available that way, so `--command`/`sh -c` is required regardless once more than one `mc` invocation is needed in one pod.
  2. **`kubectl run --rm -i --restart=Never` can lose a fast command's stdout entirely, a genuine attach race, not a display quirk of `--quiet`.** Reproduced live, deterministically: `mc alias set ... && mc ls local` (no delay) produced completely empty output on 3/3 runs; the exact same command with a `sleep 1` inserted between the two succeeded and showed the real listing on 3/3 runs. The pod's own exit code is unaffected either way (only what gets displayed via `kubectl`'s attach), which is why this specifically breaks `bucket list` (whose whole point IS the displayed output) while leaving `bucket create`/`rm`'s correctness (checked via exit code) unaffected. Fixed by adding `sleep 1` before the real command in `_saas_minio_mc_run`. If a future change removes this sleep "for speed," expect `bucket list` to intermittently or consistently show nothing despite buckets genuinely existing.
- **The same-cluster E2E workaround's already-documented gap (see the `services/vault/` note above on `eso-round-trip`'s "ESO-to-Vault data fetch... left unverified") reproduces identically for `saas vault integrate minio`'s own equivalent E2E phase (`integrate-vault-full`), confirmed live, not just by analogy.** ESO's `ClusterSecretStore` fails with `could not create client: ... dial tcp: lookup <vault-release>.vault.local ...: server misbehaving`: nothing patches CoreDNS to resolve VAULT's own external domain from inside a cluster that also happens to host the ESO consumer (unlike a consumer's OWN domain, which `_saas_gitlab_cluster_patch_coredns` does patch, for GitLab specifically). Every step through rendering/applying the `SecretStore`/`ExternalSecret` succeeds for real (confirmed live); only the final ESO→Vault fetch needs either two genuinely separate clusters or a manual CoreDNS `hosts` entry, neither available in a single-host test run. `tests/minio/e2e/run-tests.sh`'s `integrate-vault-full` phase reports this as an informational note, not a test failure, matching how the pre-existing gap is treated for GitLab.
- **`saas gitlab install --object-storage external`'s "full replace" claim is verified live, not just by code inspection**: `tests/minio/e2e/run-tests.sh --only dev-install,integrate-gitlab-full` confirms, against a real cluster, that no `<gitlab-release>-minio` `Deployment` gets created, that GitLab's `<release>-datastore-minio` Secret carries MinIO's real (not placeholder) root user, and that GitLab's full bucket set (including `registry`) exists on the shared MinIO instance after a real `helm install` of the `gitlab/gitlab` chart.

Additional validation useful before changing the values overlays, without paying for a real install:

```bash
SAAS_DOMAIN=x SAAS_RELEASE=gitlab SAAS_NAMESPACE=gitlab SAAS_INGRESS_CLASS=nginx SAAS_TLS_SECRET=x \
  envsubst '${SAAS_DOMAIN} ${SAAS_RELEASE} ${SAAS_NAMESPACE} ${SAAS_INGRESS_CLASS} ${SAAS_TLS_SECRET}' \
  < services/gitlab/values/dev.yaml.tpl | helm template gitlab gitlab/gitlab -f - --namespace gitlab >/dev/null
```

Note: `helm template` without a real cluster doesn't detect the real Kubernetes API version (`Capabilities.APIVersions`), so it may render `Ingress` with the old `extensions/v1beta1` schema instead of the real `networking.k8s.io/v1` a `helm install` against a real cluster will use. Not a bug if it only shows up in local `helm template`.
